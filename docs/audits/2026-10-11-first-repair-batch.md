Actionable findings produced additional RED tests and repairs: legacy `str(dict)` deposits, processing-time expiry versus payment time, cancellation/expiry locking, remote-session compensation on local commit failure, zero-price subscription joins, separate paid checkouts mistaken for retries, and live-session identity drift. ## Release gates and operational limits

1. **PostgreSQL concurrency:** run controlled simultaneous webhook/status/cancel/expiry and separate-live-checkout interleavings on an isolated PostgreSQL database. SQLite and SQL-shape checks do not establish production locking behavior.
2. **Provider test-mode journey:** use an isolated Stripe test environment from checkout creation through signed events, persisted entitlement/escrow and browser readback. Confirm webhook version/fields and checkout expiry behavior. No real customer charge belongs in acceptance.
3. **Reconciliation:** collected payments for cancelled/ended/duplicate entitlements return 409 requiring support; they are not silently completed or automatically refunded by these rejection paths. Historical live intents without an intended session ID also need reconciliation. A durable operator queue and automated receipt-bound refund workflow are not implemented by this batch.
4. **Ambiguous remote outcomes:** a known checkout is expired if its local commit fails; an expiry failure logs the provider session reference for reconciliation. URLs are returned only after commit and new sessions expire after approximately 31 minutes. An unknown provider response/crash can still leave an orphan session; there is no durable checkout-intent saga or recovery across client retries. Do not describe this as exactly-once provider execution.
5. **Release checks:** exact-head hosted CI, dependency parity and authenticated frontend checkout/post journeys are still required. No frontend, wind, forecast, provider configuration or deployed state was changed. This report does not supersede Claude's pending acceptance work.
