# Amendment 1 to served-wave-verify-v1 (build rulings)
Stamp: 2026-11-23. These are the advisor's rulings on the build (#1177), as relayed by the director session on 2026-11-23. They were written before any record exists: nothing has been collected, no repo variable is set and no bucket is written. Where this file and `served-wave-verify-v1.md` (#1168, `cae692737`) differ, this file holds. Every other rule is unchanged.

| # | Rule | Ruling | Where it is built |
|---|---|---|---|
| A1 | Stuck-sensor flag (sections 0.1 and 7) | **Changed.** The 6-in-a-row stuck rule applies to the CONTINUOUS fields only: WVHT, APD, SwH and WWH. It never applies to the binned periods (DPD, SwP, WWP) or to the binned and compass directions (MWD, SwD, WWD). A steady swell repeats those for hours, and that is a real report. Pinned by a steady-swell test (10 h of constant DPD 14.81 s and MWD 285°, plus constant SwP, WWP, SwD and WWD: nothing flagged, the pairs scored `ok`). | `point_archive/qc.py` `STUCK_EXEMPT`; `tests/test_point_archive_shared.py`, `tests/test_served_wave_scorer.py` |
| A2 | Record unit, file layout and storage (sections 0.1, 6 and 9) | **Changed.** One record per (model, run, frame set, tier, buoy, lead). A partition set's values go in its own record (`partitions: [{kind, h, tp, dir}]`), with that set's own frame hash, grid hash, cell and status. Why: the sets of one model sit on different runs (live 2026-11-22: EURO waves on the 12Z ECMWF run, EURO swell sets on the 00Z CMEMS run), and one record cannot carry two sets' provenance. **The run file is gzipped JSONL in the SLIM layout `slim/1`:** a header line holds the run provenance shared by every record, one line per frame holds its provenance, one line per grid snapshot holds the buoy cells, and each record keeps only what is its own. It is lossless: a reader gets back exactly the `point-archive/1` rows the sampler built (tested), so the record schema and the scorer are unchanged. Columnar storage is not adopted: it would add a parquet / arrow dependency, and a decoder in the CI scorer, for little further saving. Section 9 is **restated**: about **0.125 GB a month** at 3 publishes a day (measured on synthetic rows at the live lead counts and the frozen 100-station list: one run of GFS + ICON + EURO = 93,936 records, 1.41 MB in the slim layout against 3.31 MB in the plain one), about **4.5 GB over 36 months**. The first-week budget check now pauses collection when the measured volume exceeds **2 × 0.125 = 0.25 GB a month** (pro rata for the week), and the director is told before it continues. The quota and cost check owed before the dispatch request is made against these figures. | `point_archive/served_sampler.py`, `point_archive/slim.py`, `writer.write_run` / `read_run_rows`; tests `test_point_archive_shared.py`, `test_served_wave_sampler.py`; log `2026-11-23-opus-served-wave-verify-build.md` |
| A3 | Weekly snapshot PR (section 7a) | **Changed.** The weekly snapshot PR is opened with a fine-grained PAT referenced by NAME (secret `SERVED_WAVE_VERIFY_PR_TOKEN`: this repository only, contents and pull requests read/write), never with the workflow's `GITHUB_TOKEN`. GitHub runs no workflow on a push or PR made with `GITHUB_TOKEN`, so CI would never run on the snapshot PR. While the secret is unset, the snapshot step is skipped with a warning. Creating the secret is the owner's step. | `.github/workflows/served-wave-verify-score.yml` job `snapshot`; `tests/test_served_wave_workflows.py` |
