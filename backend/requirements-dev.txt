# ⛔⛔ fastmcp IS DELIBERATELY NOT HERE, AND MUST NOT BE ADDED.
# `weather_sim_mcp.py` and `services/weather_pipeline/sim_boot.py` import it, so six test modules
# need it — but fastmcp's dependency tree is fundamentally NEWER than this app's pinned stack and
# installing it into the test environment breaks the app itself. Measured in CI, 2026-08-01:
#
#   * every published fastmcp — 3.3.1, 2.11.3, 2.10.6, 2.8.1, 2.6.1, 2.3.4, 2.2.10 — requires
#     httpx>=0.28.1, while requirements.txt pins httpx==0.27.2. No version satisfies both, so this
#     is not a version-selection problem that a better pin can solve.
#   * forcing it in anyway ALSO lifts starlette, and `routes/social/__init__.py` then dies with
#     `TypeError: Router.__init__() got an unexpected keyword argument 'on_startup'` — so
#     test_spot_ratings.py and test_surf_spots_live_security.py stop importing. Adding fastmcp
#     costs two modules to gain six, and silently changes the stack under everything else.
#
# ⇒ The composition guard suite in ci.yml EXCLUDES the six fastmcp-dependent modules BY NAME and
#   says so in its floors. The parity monitor installs fastmcp separately because the probe imports
#   weather_sim_mcp and never imports routes/, so the newer stack is harmless there.
# ⇒ The durable fix is upstream and is a real decision, not a chore: either raise httpx/starlette
#   in requirements.txt (both transitive via supabase/openai/fastapi — wants review), or stop
#   importing fastmcp at module level in weather_sim_mcp.py so the sim's pure logic is importable
#   without an MCP server framework. The second is the smaller change and the better shape.
#
# Pinned to the versions the 2026-08-01 baseline was measured with (38 modules, 545 passed,
# 64 skipped, 0 failed).
