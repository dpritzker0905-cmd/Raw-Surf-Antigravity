# Test/dev dependency OVERLAY — 2026-08-01.
#
# ⚠️⚠️ INSTALL THIS *AFTER* requirements.txt, NOT INSTEAD OF IT, AND NOT VIA `-r requirements.txt`.
#     pip install -r requirements.txt
#     pip install -r requirements-dev.txt
# The two-step order is load-bearing (see the httpx note below) — a single resolution over both
# files is ResolutionImpossible, which is exactly how the first cloud run of the parity monitor
# died.
#
# WHY THIS FILE DID NOT EXIST UNTIL NOW: no pytest ran in GitHub Actions at all, so nothing ever
# had to declare what the suite needs. The backend suite was runnable only on a machine where
# these had been installed by hand at some point — a state indistinguishable from "the tests pass"
# right up until someone checks out the repo clean, which is what a CI runner does every time.
#
# Discovered by wiring the composition guard suite to CI and reading the collection errors:
#   fastmcp    weather_sim_mcp.py and services/weather_pipeline/sim_boot.py import it at module
#              level; four guard modules could not be collected without it.
#   aiosqlite  backend/database.py and services/weather_pipeline/spot_ratings.py import it — the
#              SQLite lane tests and local dev run on. Production serves Postgres via asyncpg,
#              which is why requirements.txt never needed it and why its absence stayed invisible.
#
# ★★ THE httpx DIVERGENCE IS DELIBERATE AND IS THE WHOLE REASON THIS IS AN OVERLAY.
# requirements.txt pins httpx==0.27.2. EVERY published fastmcp release — checked back to 2.2.10,
# and 2.3.4 / 2.6.1 / 2.8.1 / 2.10.6 / 2.11.3 / 3.3.1 all agree — requires httpx>=0.28.1. There is
# therefore NO fastmcp version installable alongside the declared production pins, so no amount of
# version-chasing fixes this; the local machines where the sim tests "passed" simply had a drifted
# httpx that no longer matched requirements.txt.
# The test lane consequently runs a NEWER httpx than production. That is a real fidelity gap and it
# is named here rather than hidden: the composition guards exercise offline rating/geometry logic
# and do not touch the HTTP client, so the risk is bounded — but anything added here that DOES
# exercise httpx behaviour is not testing what production runs.
# ⇒ The durable fix is upstream: either raise httpx in requirements.txt (it is a transitive
#   dependency of supabase/openai and wants review), or stop importing fastmcp at module level in
#   weather_sim_mcp.py so the sim's pure logic is importable without an MCP server framework.
#
# Pinned to the versions the 2026-08-01 baseline was measured with (44 modules, 737 collected,
# 673 passed, 64 skipped, 0 failed).
